## pool-flake-reentrant-tracker — a previous test's cyclic semaphore garbage made the next pool test fail with 5 reentrant-ResourceTracker unraisable warnings
- **Date:** 2026-10-10
- **Symptom:** `tests/test_pool.py::test_a_dying_worker_surfaces_as_broken_pool_and_is_replaced` intermittently FAILED in `make verify` (`-n 8`, `filterwarnings = ["error"]`) with `1 failed, 694 passed`, while its own assertions passed (log: `worker.replaced slot 0 cause broken_pool`); retries passed. About 2 of 20 natural `-n 8 --cov` runs on the dev host.
- **Error patterns:** ExceptionGroup multiple unraisable exception warnings (5 sub-exceptions), PytestUnraisableExceptionWarning, Exception ignored in: <Finalize object, dead>, UserWarning ResourceTracker called reentrantly for resource cleanup, The semaphore object '/mp-...' might leak, ReentrantCallError Reentrant call into the multiprocessing resource tracker, resource_tracker.py ensure_running, synchronize.py _cleanup, flaky, intermittent, retry passes, BrokenProcessPool, ProcessPoolExecutor
- **Root cause(s):** (1) test code: `test_a_wedged_build_is_terminated_and_its_worker_replaced` kept `manager` (the killed executor's `_ExecutorManagerThread`, holding its call and result queues = 5 named SemLocks) in a local, and `asyncio.run` raising BuildTimeout through `pytest.raises` leaves that frame in a BuildTimeout -> traceback -> Task cycle, so the 5 SemLocks outlived the test as cyclic garbage (the only such garbage in the suite); (2) CPython 3.12.15 gh-109629: a cyclic GC landing on a thread inside `ResourceTracker.ensure_running`'s RLock (the next test's SemLock `register` or a spawn's `getfd`) runs the SemLock finalizers reentrantly -> ReentrantCallError -> `_send` UserWarning; (3) config: `filterwarnings = ["error"]` turns the warning into an exception in the finalizer, which pytest's unraisable plugin charges to whichever test is running (the next one in file order). Not CPU load from tests/test_bench.py (eliminated).
- **Fix:** `del manager` in the wedged test right after its last use (tests/test_pool.py, commit ef37f23), with a comment carrying the mechanism and the numbers; the queues now die by refcount on the main thread outside any tracker lock. No product code changed.
- **Files changed:** tests/test_pool.py, docs/tech_debt/resolved/2026-10-06-test-pool-dying-worker-flake.md (moved from active/), docs/tech_debt/INDEX.md
- **Reproduction:** forced-GC plugin `pf_force_first` (one `gc.collect()` inside the first locked `ResourceTracker._check_alive` of each test), source and command in docs/tech_debt/resolved/2026-10-06-test-pool-dying-worker-flake.md, Resolution: `PYTHONPATH=<dir> .venv/bin/python -m pytest -p pf_force_first tests/test_pool.py -n0 --no-cov` gives `1 failed, 16 passed` before the fix, `17 passed` after. Forcing the GC in every locked section instead hides the bug (it collects the young cycle before the creating test returns).
- **Why not caught:** no gate existed for this class: `make verify` sees the symptom only when GC timing lines up, and nothing checks that a test leaves no named semaphores to the cyclic GC; the failure is charged to the wrong test, so the first suspicion went to host CPU load.
- **Recurrence guard:** the comment at the `del manager` in tests/test_pool.py (test_a_wedged_build_is_terminated_and_its_worker_replaced) names the mechanism; the forced-GC procedure in the resolved debt record reproduces the class on demand; this entry. Hint for a new match: an unraisable finalizer warning charged to a test usually comes from garbage an EARLIER test in the same xdist worker left behind -- trace where the objects were created, not where they were freed. No automated regression test, deliberately (reason in the debt record).
