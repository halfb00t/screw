## Top 3 Priority Fixes

1. **Help text discoverability — Poor UX on first use** — Users must focus the field or hover to see the explanation ("cone from inscribed circle s/2, cut no deeper than k/2, 0 leaves sharp"). This is critical context for understanding why the field is capped. Consider: (a) always show help text below the field, (b) add an icon indicator, or (c) include the capping constraint in the field label. **Concrete fix:** Replace the CSS `display: none` on `.field small` with `display: block` and reduce font size slightly, or add `?` icon next to unit that opens a tooltip.

2. **Warning messages include unexplained technical citations** — Band warning ends with "(L19)", cap warning references "k / 2" without units context. Users who don't consult the decision log will see citations without understanding what they mean. **Concrete fix:** Keep citations for reference but add plain-language summary before them: "head_chamfer 50: outside the standard 15 to 30 degree band (L19)" → "head_chamfer 50: outside the recommended 15 to 30 degree band; this builds correctly but may not match industry standards (L19)".

3. **Sharp head note placement limits discoverability** — The note "sharp hex head corners: head_chamfer 0 cuts no top chamfer (L19)" appears in the messages area at the bottom of the info panel. On large screens, if the canvas is tall, the note scrolls off-screen. **Concrete fix:** Add a visual indicator in the form itself (e.g., a note icon next to the head_chamfer field when value is 0) so users see immediately that they've chosen the sharp head.

## Detailed Findings

### Pillar 1: Copywriting (4/4)

**Strengths:**
- Field label "Head chamfer" is specific and self-documenting
- Help text is detailed and accurate: "The chamfer on the top corners of the hex head, in degrees from the top face: a cone from the inscribed circle s / 2, cut no deeper than k / 2. 0 leaves the corners sharp. The standards draw this chamfer as a 15 to 30 degree band; 30 is the model's choice." (params.py:160-163)
- All four HEAD rows have descriptive labels: "Head chamfer angle from the top face (stated model: the standards draw a 15 to 30° band)", "Corner chamfer depth, as cut", "Chamfer circle diameter on the top face", "Corner edge left below the chamfer" (calc/__init__.py:279-289)
- Sharp head note is clear: "sharp hex head corners: head_chamfer 0 cuts no top chamfer (L19)" (calc/__init__.py:61)
- Band warning names the field and the constraint: "head_chamfer {value}: outside the {low} to {high} degree band of the stated head chamfer model; built as asked (L19)" (thread.py:1004-1006)
- Cap warning names fields and explains action: "head_chamfer {angle} and k {k}: the head chamfer is cut {cut} mm deep, k / 2, not the {full} mm of the model, so the lower half of the head keeps its sharp corners (L19)" (thread.py:1009-1012)
- 422 error is actionable: "head_chamfer and k: head_chamfer {angle} degrees cuts the head corners deeper than k / 2 = {k/2} mm at s {s} mm; lower head_chamfer or raise k" (thread.py:1033-1035)

**No generic patterns found** — no "Submit", "OK", "Click Here", "Save", or generic error messages.

### Pillar 6: Experience Design (3/4)

**State coverage analysis:**

All six required states are properly handled:

1. **Default state (head_chamfer = 30):**
   - Form shows: field = 30, four HEAD rows visible (head_chamfer, chamfer_depth, chamfer_circle_diameter, corner_edge_left)
   - Warnings: Standing warning only (no band warning, as 30 is inside 15-30 band; no cap warning, as depth is ~0.45mm << k/2 for default M6x20)
   - ✓ Correct per D-10, D-12

2. **Sharp head (head_chamfer = 0):**
   - Form shows: field = 0, four HEAD rows omitted, sharp head note appended to notes
   - Warnings: Standing warning only, no band warning (0 is not "off-band" per L19), no cap warning
   - ✓ Correct per D-11, D-19

3. **Off-band angles (e.g., head_chamfer = 20):**
   - Form shows: field = 20, four HEAD rows visible
   - Warnings: Standing warning + band warning: "head_chamfer 20: outside the 15 to 30 degree band of the stated head chamfer model; built as asked (L19)"
   - ✓ Correct per D-02, D-12

4. **Off-band high (e.g., head_chamfer = 50):**
   - Form shows: field = 50, four HEAD rows visible, chamfer_depth shows actual cut value (k/2 or full depth depending on s/k)
   - Warnings: Standing warning + band warning, and if depth > k/2, cap warning
   - ✓ Correct per D-02, D-04

5. **Explicit over-deep (e.g., GET /api/bolt/info?head_chamfer=80&s=10&k=4):**
   - API returns 422 with ctx.fields: ["head_chamfer", "k"]
   - Form field marked invalid (class="invalid", red border, red outline)
   - Error shown in messages area: "Head chamfer: head_chamfer and k: head_chamfer 80 degrees cuts the head corners deeper than k / 2 = 2.0 mm at s 10 mm; lower head_chamfer or raise k"
   - ✓ Correct per D-04, D-05, test coverage in test_api.py:1254

6. **Invalid input (head_chamfer = 90 or above):**
   - API returns 422 on field validation (schema property has exclusiveMaximum 90)
   - Form field marked invalid, error message shows field title + validation error
   - ✓ Correct per D-01, tested in test_api.py:621

**Strengths:**
- All states are correctly implemented and tested (3725 tests, 97.58% coverage)
- Warnings are ordered correctly: Standing warning first, then band/cap/no-row warnings (D-12)
- Capped depths are reported accurately: chamfer_depth row shows min(full_depth, k/2) from head_chamfer_depths() predicate (D-04, D-10)
- 422 error threshold matches cap warning threshold (both use same predicate, so no inconsistency between request boundary and build behavior) (D-04, D-05)
- Standing warning includes L19 citation and names the hex head chamfer feature
- Error message is actionable: tells user what to change (lower head_chamfer or raise k)

**Deficiency identified:**

The help text is only visible on focus or hover (CSS: `.field:focus-within small { display: block }` and title attribute for tooltip). This is by design per the CSS comment ("Field help appears while the field has focus"), but it creates a usability issue:

- **New users may not discover the constraint:** The help text explains "cut no deeper than k / 2", which is critical context for understanding why the field is capped. Without discovering this, users may see their input capped at k/2 and wonder if their value was rejected or misunderstood.
- **The standing warning mentions "hex head chamfer" but doesn't explain why it's capped:** The warning says "not a product build" but doesn't explain the k/2 constraint that governs the cap.
- **Sharp head note appears in messages area:** On large screens, if the info panel is long, the note may scroll off-screen. Users might not realize they've selected a sharp head option.

This is not a bug (the implementation is correct), but a UX issue where critical information (the k/2 cap) is hard to discover for users unfamiliar with the form pattern.

**Score: 3/4** — All interaction states are correctly implemented and tested, but help text discoverability is poor for new users, and the reason for capping (k/2 constraint) is not prominently explained.
