# Phase 06.1: Code Review Report

**Reviewed:** 2026-10-24
**Depth:** standard (diff `c9ad5a9..HEAD`)
**Files Reviewed:** 17
**Status:** issues_found

## Summary

The change is sound where it matters most. I checked `head_chamfer_volume` against an independent
200-point Gauss-Legendre quadrature over 300 random `(s, k, angle, depth)` rows. The rows included
angles from 0.001 to 89.999999 degrees and capped and uncapped depths. The worst relative error
was 7.6e-14. The cutter geometry in `bolt.chamfer_head` is consistent with the integrand. The
cap, the 422 rule and the warning all read the one predicate `head_chamfer_depths`, so they cannot
disagree at the `k / 2` boundary. The boundary tests are real. The explicit-value rule reads `s`
and `k` from the frozen defaults as D-05 requires. `make verify` passed (3716 tests, coverage
97.56%).

I found no BLOCKER. Two WARNINGs remain: one on the info document against the refused build,
which includes the observation you asked about, and one on a silent sharp-head default in
`bolt.assemble`.

### The `head_chamfer=5e-324` observation

Verdict: not a BLOCKER, and the printed `0` is not a wrong number. It is still a defect worth a
WARNING (WR-01), and the real defect is wider than the one value.

What I ran:

- `derive(BoltParams(head_chamfer=5e-324))` prints `chamfer_depth` 0.0, `corner_edge_left` 4.0
  and `chamfer_circle_diameter` 10.0. The volume row is withheld.
- `build(...)` raises `BuildError("Geometry kernel failed (ValueError); ...")`, and the API turns
  that into 422 `build_error`. D-18 explicitly allows this outcome.

Why the 0 itself is acceptable for L02:

- `min((corner - s/2) * tan(5e-324 deg), k/2)` is 0.0 in double precision (`thread.py:339-341`).
  That is the formula's true value at that angle.
- No part ships for it. `solid/__init__.py:465-466` calls `head_chamfer_volume` before the
  kernel, and the call raises `ValueError` (`thread.py:249-251`).
- The 422 is not a "plausible wrong number".

Where it does fall short of L02 and the IN-01 precedent in the same function (`calc/__init__.py`,
the `buildable` block): the info document does not say the part cannot be made. See WR-01.

## Warnings

### WR-01: Info document prints chamfer rows and a volume for angles the builder refuses, with no "not built" warning

**File:** `src/screw/calc/__init__.py:94-108` and `:140-141`; `src/screw/solid/__init__.py:465-466`

**Issue:** Three related defects, all on the same path.

1. **Tiny angles (the observation).** The builder refuses `head_chamfer` below roughly 1e-5
   degrees. I ran the build at 1e-5, 1e-10, 1e-20, 1e-50, 1e-100, 1e-200, 1e-300 and 1e-320.
   Each gives `BuildError` (piece gate relative error -0.35 at 1e-5, `Standard_Failure` below
   that). 1e-4 and above builds. For those same angles `derive()` returns a full document: four
   chamfer rows and a finite closed-form volume (804.7065 mm3 at 1e-5 and below). The only
   warning is the off-band one.
   - `_bolt` already refuses to print `turns` and `volume` for a thread shorter than
     `MIN_TAIL_MM`, because "a volume row would be a number for a bolt nobody can make", and it
     adds "this part is not built". The chamfer path does not follow that rule. Its own test
     says the info document and the build should agree on what is a part
     (`test_a_length_below_the_floor_is_a_warned_info_document_and_a_422_build_error`).
   - D-18 fixes the build outcome (no floor, named `BuildError`). It does not require the info
     document to stay silent about it.

2. **At 5e-324 the volume is withheld for a false reason.** `head_chamfer_volume` raises
   `ValueError`, which the `compute()` loop turns into NaN. The warning then reads "volume not
   reported: the closed form ... is not a finite number for these parameters". The closed form
   is not non-finite. The oracle refused an angle whose tangent underflows. Meanwhile
   `chamfer_depth` 0.0 and `corner_edge_left` 4.0 are printed for the same part. The reader
   gets a document that says "no chamfer, edge left 4 mm" next to a vague volume warning.

3. **The refusal message is misleading.** `solid/__init__.py:465-466` raises the `ValueError`
   before the kernel runs, but `_build_checked` wraps it as "Geometry kernel failed
   (ValueError); check d, pitch, ... and head_chamfer". The kernel never ran.

Which tiny angles build is a single macOS arm64 measurement (the test says so at
`tests/test_solid.py`, `test_a_tiny_or_near_right_head_chamfer_builds_inside_its_gates_or_is_refused_by_name`).
A shared link with `head_chamfer=3e-5` may build on one host and 422 on another. The info
document gives no hint of that either.

**Fix:** Keep D-18 (no floor in the model). Make the info document honest about the refusal.
The smallest change is to treat "the chamfer oracle cannot be judged" like the thread-floor case:

```python
# in _bolt, next to `buildable`
chamfer_ok = True
if p.head_chamfer > 0:
    try:
        head_chamfer_volume(p.s, p.head_chamfer, head_chamfer_depths(p.s, p.k, p.head_chamfer)[1])
    except (OverflowError, ValueError):
        chamfer_ok = False
        warnings.append(
            f"head_chamfer {_plain(p.head_chamfer)}: too small for the head chamfer to be "
            "modelled, so this part is not built; chamfer rows and volume not reported")
# skip chamfer_rows and "volume" when not chamfer_ok
```

For the kernel-refused band (1e-5 to 1e-4), either add a single warning for `0 < head_chamfer <
1e-3` ("may be refused by the geometry kernel") or file a `docs/tech_debt/active/` item with
severity "must". Also reword the `solid/__init__.py` failure for an oracle `ValueError` so it does
not say "kernel failed".

### WR-02: `bolt.assemble(..., head=None)` silently builds the sharp head the product no longer ships

**File:** `src/screw/solid/bolt.py:118-127`; consumers `bench/head_fuse.py:89-97`, `bench/end_cuts.py:309,322,388`

**Issue:** `assemble` keeps a default `head=None` that fuses the sharp prism "for bench/ and tests".
The phase exists so that the Phase 7 re-sweep "measures the chamfered head" (CONTEXT, Domain). But
`bench/head_fuse.py::assemble` still calls `bolt.assemble(p, thread)` with no head. Its docstring
says "`_build` calls exactly this code ... in the product's order". That is now false. The bench
builds `BoltParams` with the default 30 degree chamfer and then fuses a sharp head. Its closed form
(`closed()`) has no chamfer term, so the bench stays self-consistent and nothing fails. It will
report fuse timings and volume errors for a part the product no longer builds. A silent default is
the wrong shape for this, since the repo's own rule is that a part must not quietly differ from its
parameters (L02).

**Fix:** Make `head` required, and add a `sharp` helper for the callers that want the old part.
mypy `--strict` then names every caller, as `bolt_end_closed_volume` already does for
`head_chamfer`.

```python
def assemble(p: BoltParams, bare_thread: cq.Solid, head: cq.Shape) -> cq.Shape: ...
# callers that want the sharp head say so: bolt.assemble(p, thread, bolt.head_prism(p))
```

In `bench/head_fuse.py` and `bench/end_cuts.py`, either pass the chamfered head
(`bolt.chamfer_head(p, bolt.head_prism(p), cut)`) or correct the docstring and mark the sweep as
sharp-head. Do this before Phase 7 reads the numbers.

## Info

### IN-01: `PAST_TOP` is a local copy of `nut.PAST_FACE`

**File:** `src/screw/solid/bolt.py:14-17` (the constant), `src/screw/solid/nut.py:36`

**Issue:** The comment gives a reason (nut imports bolt, so bolt cannot import nut). That leaves two
copies of one overshoot value, free to drift. Cheap to fix: put the constant in a module both
already import (for example `screw.solid.helical` or `screw.calc.thread`).

**Fix:** Define `PAST_FACE` once in a shared module and import it in both.

### IN-02: Two D-18 tests accept any outcome

**File:** `tests/test_api.py` (`test_a_tiny_head_chamfer_is_a_422_build_error_or_a_200_never_a_500`);
`tests/test_solid.py` (`test_a_tiny_or_near_right_head_chamfer_builds_inside_its_gates_or_is_refused_by_name`)

**Issue:** The `1e-6` API request is asserted `status_code in (200, 422)`. The solid test treats
build and refusal as equal for every tiny angle. That is an honest reflection of D-18, and both
tests do pin 5e-324 as refused. But neither can fail if the refusal threshold moves or if a refused
angle starts building a wrong part inside the gates. The threshold (about 1e-5 degrees on macOS
arm64) is the thing WR-01 turns on.

**Fix:** Pin the measured boundary with a two-sided check (builds at 1e-3, refused at 1e-6), marked
as platform-dependent only if linux CI shows a difference. Otherwise the tests keep their shape.

### IN-03: `contextlib.suppress(OverflowError, ValueError)` around the head warnings can only hide a bug

**File:** `src/screw/calc/__init__.py:140-141`

**Issue:** `head_chamfer_warnings` is plain arithmetic on validated floats. It raises neither error
for any instance the model accepts. The comment concedes only a `model_construct` instance can
reach it. For such an instance the suppress silently drops the band warning with no trace, so a
real error would vanish. Prefer the narrower guard that the sibling rows use (the NaN-to-warning
path), or drop the suppress and let `derive`'s contract tests catch it.

**Fix:** Remove the suppress, or replace it with a `try/except` that appends
`"head_chamfer warnings not reported: ..."`.
