## Decisions this plan makes, and why

The planner measured four candidate edits of navigate's rebuild block on 2026-10-21 at HEAD `3eb2920`, each served in place of app.js through the probe's `SCREW_PROBE_APP_JS` override (results in § Reproduction probe):

| Candidate | Edit | Probe failures | Pin |
|---|---|---|---|
| BASE | none | 5: the three WR-09 window steps and the two `schema-window:` steps | fails |
| A, the review's patch | `clearPicker();` after `dropMesh();`, before `await buildForm(kind)` | 2: `schema-window:` (the bolt form is still live) and `back-schema:` (the bolt is left with no picker and no badge) | fails |
| B, clear after the form | `clearPicker();` directly after `if (!(await buildForm(kind))) return;` | 2: both `schema-window:` steps | fails |
| **C, this plan** | `clearForm(); clearPicker();` after `dropMesh();`, before `await buildForm(kind)` | none, and 05-23's probe passes 17/17 | passes |

- **Why not A alone.** Back while the nut's schema loads: the overtaken navigation never replaced the form, so `formKind` is still `bolt`, navigate's rebuild condition is false for the Back, and the bolt keeps its form with the picker A removed (`{hidden: true, selects: 0, badge: ''}`) until the next kind change.
- **Why not B.** It closes WR-09 exactly, but leaves the schema half of the same window open. While the schema is in flight the bolt's form and picker are live and `formKind === currentKind`, so a pick runs the bolt's whole update after `dropMesh()`: it writes the bolt hash over `#kind=nut`, builds the bolt, and the finished nut (empty clearance) shows that bolt under `Showing the last valid part`. That is the exact case rule 36 (R10, T-05-23) exists to prevent. It predates this plan and nobody filed it; the planner measured it while choosing the placement.
- **Why C.** With the form cleared too, `formKind` is null for the whole switch: no old control or select exists to act on, `update()` returns (the 05-23 guard, unchanged), and an overtaking navigation finds `kind !== formKind` and rebuilds the kind it names whole (05-23's rebuild condition, unchanged). A kind switch then looks exactly like a first load. That is what UI Considerations E3 `loading` ("the form is blank while `/api/schema?kind=` is in flight") and E11 `loading` ("the picker is hidden while `/api/presets?kind=` is in flight") already say. Those two rows were false on a kind switch until now, and stay unedited. CLAUDE.md: a choice between stability and a smaller diff takes stability and says so; this is that choice, flagged for the owner below.
- **Not a guard in `pick()`.** It would leave a live-looking picker that ignores input, a muted control rather than a removed one, and would not touch the schema half.
- **The why comment goes above `dropMesh();`**, in the block's existing comment, so the squashed pin `dropMesh(); clearForm(); clearPicker(); if (!(await buildForm(kind))) return; try {` stays contiguous. Comments name functions without an opening parenthesis: the pin counts `clearForm(` and `clearPicker(` by pattern, and the file-wide `dropMesh()` count is 2.
- **The `rowOfFields` comment is rewritten, its statements are not.** Its comment says the catalogue stays the old kind's until a kind switch's fetch lands, and that stops being true. The IN-06 guard stays as a second line (05-23 prohibition).
- **One code commit.** The code, the pin and the three UI-SPEC rules form one concern, "a kind switch takes the old kind's form and picker off screen before it fetches the new ones", like 05-23's WR-08 commit. The disposition flip is a second, docs-only commit, because it names the first one's sha.
- **Reversibility.** Page state only. Falling back to B is a two-line revert plus the pin string and the two `schema-window:` probe steps.
