## Phase Goal

ROADMAP **Goal** (verbatim; not in user-story form, so the MVP user-story framing is not invented
here): Every configuration a user is allowed to ask for builds inside a per-build timeout measured on
linux/amd64 over the full grid, or is capped and warned or refused with a `422`, and every runtime
bound cites the run that set it.

phase was told to gate), the published refusal shape (B-02), and how D-06's cap of a defaulted value
applies (B-03). Record the rulings.

Purpose: CONTEXT keeps the budget open on purpose; D-05 marks the model costly to reverse; the 422
`type` is a published contract. Output: `07-OWNER-RULINGS.md`.
</objective>

    the count), which shareable links start returning a 422, and the admitted set from which the
    timeouts (D-09) and the worker count (D-03) are measured. Undoing it later means a new sweep and a
    superseding entry, and links that worked under one budget may refuse under another.
  </context>

<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 2: B-02, the refusal shape every front end returns</name>
  <decision>The 422 `type` and body for an artifact over its budget, now that the preview STL and the STEP can be refused too</decision>
  <context>
    Today only the fine STL is refused and its type says so (`fine_stl_cap`). D-06 refuses each
    artifact against its own budget. The text already begins with the field names (the CLI prints no
    `loc`). L02 asks a 422 to name the fields; today's body has no `ctx.fields`, while the
    explicit-conflict 422s (`thread_length_conflict`, `head_chamfer_conflict`) carry them. A type
    string is part of the published API (L19 treats it as costly to change), so whichever is chosen is
    listed in L21.
  </context>
  <options>
    <option id="over-budget">
      <name>One type `over_budget` for all three artifacts, with `ctx.fields` and `ctx.artifact`</name>
      <pros>True for every artifact; names the fields like the other 422s; one string for clients to read.</pros>
      <cons>Retires `fine_stl_cap`, a published type; clients that matched it must change.</cons>
    </option>
    <option id="keep">
      <name>Keep `fine_stl_cap` for every artifact, add `ctx.fields`</name>
      <pros>No published type changes.</pros>
      <cons>The type is false for a refused preview or STEP.</cons>
    </option>
    <option id="per-artifact">
      <name>One type per artifact: `stl_preview_over_budget`, `stl_fine_over_budget`, `step_over_budget`, with `ctx.fields`</name>
      <pros>A client can tell which artifact was refused from the type alone.</pros>
      <cons>Three published strings instead of one; the artifact is already in the request.</cons>
    </option>
  </options>
  <resume-signal>Reply `B-02: over-budget`, `B-02: keep` or `B-02: per-artifact`</resume-signal>

<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 3: B-03, how a defaulted value that pushes a part over is capped and warned (D-06)</name>
  <decision>Which fields the D-06 cap may move when the request did not name them, and whether the capped part is the whole part or only the over-budget artifact</decision>
  <context>
    D-06 is locked: a defaulted value that pushes a part over is capped and warned; an explicit request
    over budget is a 422. The table's D-06 section lists, per candidate, the refused points whose
    trimmable fields or pitch sit at their frozen defaults and whether moving them on their form step
    would admit them. Explicit-versus-default is known only at the request boundary (app and CLI), so
    the cap runs there, from the same explicit-key set the conflict rules read. A trimmed length or
    height keeps the thread the user asked for; moving a defaulted pitch changes which thread it is.
  </context>
  <options>
    <option id="part-wide">
      <name>Part-wide cap of defaulted lengths (recommended)</name>
      <pros>Bolt `thread_length` then `length`, or nut `m`, when not named, is capped to the largest value on its form step at which every artifact fits, with one warning naming the field, its default and the capped value; the info document, the preview, every download and the file name come from the one capped part, so every printed number matches the file (L02). `d`, `pitch`, `s`, `k`, `clearance`, `head_chamfer` and hand never move.</pros>
      <cons>A user who wanted only the preview gets a part shortened to the strictest artifact's budget.</cons>
    </option>
    <option id="per-artifact">
      <name>Per-artifact cap of defaulted lengths</name>
      <pros>Only an over-budget artifact is built from a capped part; its `downloads[]` entry warns; the info document and the preview stay at the default when they fit.</pros>
      <cons>A download can differ from the info panel's numbers, which L02 warns against; two parts behind one link.</cons>
    </option>
    <option id="part-wide-pitch">
      <name>Part-wide cap as recommended, and a defaulted pitch raised</name>
      <pros>Also covers the case the table may show most often: a large explicit d left at the default 1 mm pitch.</pros>
      <cons>Raising a pitch changes the thread itself, not a length; the warning must say the thread differs from the default.</cons>
    </option>
  </options>
