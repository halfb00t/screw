**Hard constraints (from `CLAUDE.md`, `docs/CODING_VALUES.md`, the decision log, 01-CONTEXT):**

- Vanilla JS (one ES module) plus the vendored three.js bundle. No framework, no CSS framework, no build step except `web/` for the bundle (`make vendor-check`).
- Every number shown comes from the API (`/api/<kind>/info` `rows`, and the `warnings`, `notes` and `designation` text; `/api/presets` for the picker). The UI never computes a dimension. It never rounds one: a row value is written as `String(row.value)` (rule 23, D-19; OI-1 resolved in plan 04-13).
- The download links come from `downloads` of `/api/<kind>/info`, like every number from `rows`: per format the first entry the server does not refuse, in the server's order. The page names no format, no quality preference and no warning text of its own (rule 17, D-10), and nothing about the downloads enters the hash (D-09).
- A parameter the user did not set never silently changes the part (L02). An omitted `kind` in the hash means `bolt` forever (D-09).
- The part is not a product build yet (D-06). The first info warning on every document is the standing warning, today `plain-cut thread ends, no tip chamfer or under-head fillet; not a product build`; the page shows it verbatim like every server sentence.
- The `L/P` turn count is not shown (CONTEXT specifics).
- No per-kind label table, no field-name literal, no row-key literal and no group name in `app.js` (D-09, D-10, D-17).
- The shareable link carries millimetres and never a preset id or the page's preset basis (D-09, rule 10).

|----------|---------|------|-----------|

### Layout

- `body` is a column flex: `header`, then `main` (`flex: 1`).
- `main` is a two-column grid: `minmax(290px, 350px) 1fr`. Left: `aside` (scrolls on overflow, `--panel` surface, right border). Right: `#view`.
- `#view` is a column flex: `#canvas-wrap` (`flex: 1`, `min-height: 320px`, `--view-bg`) over `#bottom`.
- `#bottom` is a two-column grid `minmax(0, 1fr) minmax(0, 1.4fr)`: left column downloads then messages, right column the info panel `#dims`.
- `#dims` is a block: the designation `h2` (Body size, weight 700), then for each group an `h3` (the legend's role) over a `dl` that is a grid `repeat(auto-fill, minmax(12.5rem, 1fr))`, each row a wrapping flex row (`flex-wrap: wrap`, gap .75rem) with a dashed bottom border: the label `dt` takes at least half the row (`flex: 1 1 50%`) and grows into what the value leaves; extension rule 4 governs lengths, and a percentage or an `fr` is a proportion of its container and sits outside the spacing scale, as the sheet's `1fr`, `minmax(0, 1.4fr)` and `100%` already do, so the exceptions table, which lists lengths only, gains nothing; the value `dd` sits at the right (`margin-left: auto`) on the label's line when both fit, otherwise whole on its own line under the label, at the right; a value is never rounded, clipped or ellipsized to fit (rule 23); `overflow-wrap: anywhere` on `dd` is the last resort for a value wider than a whole track and takes the space before the unit first. Pinned by `test_an_info_row_drops_a_long_value_whole_under_its_label_instead_of_into_the_next_cell`.
- In the aside the order is Kind, `#picker`, `#badge`, `#counterpart`, `#params`, the action buttons. `#picker` is styled by the global `fieldset`, `legend` and `.field` rules; `#badge` is one muted Caption line, and `#counterpart` is a second one on its own line below it (an inline link after a block `p`).
- Breakpoint `max-width: 820px` (one breakpoint, no others): `main` becomes a column, `#view` moves first (`order: -1`), `#canvas-wrap` is `55vh` with `flex: none`, `#bottom` is a single column, the aside gets a top border instead of a right border.

## Spacing Scale

Declared values (all multiples of 4). The stylesheet writes them in `rem` against the browser default root of 16px (the `14px` on `body` does not change `rem`).

| Token | Value | Usage (as built) |
|-------|-------|------------------|
| xs | 4px (.25rem) | aside top padding |
| sm | 8px (.5rem) | gap between action buttons, download buttons and label/control columns; vertical margin of each `.field`; legend right padding; fit button offset |
| md | 12px (.75rem) | header gap; fieldset top margin; `#bottom` row gap; gap inside an info row (beside the label, and above the value when the row wraps) |
| lg | 16px (1rem) | header, aside and `#bottom` horizontal padding; aside and `#bottom` bottom padding |
| xl | 24px (1.5rem) | column gap of the `#dims` grid |
| 2xl | 32px (2rem) | column gap of `#bottom` |

48px and 64px are unused. Border radius is 6px on inputs, selects, buttons and message paragraphs. Border width is 1px.

**Exceptions (as built, locked, enumerated so nothing else is added).** These sub-scale `rem` values exist in `style.css` and are not multiples of 4. They stay until a deliberate cleanup (OI-8). New CSS in Phases 3 to 6 must use only the six tokens above.

| Value | Where |
|-------|-------|
| .1rem (1.6px), .15rem (2.4px) | hairline `.field` row gap; `#dims` row gap and row padding |
| .3rem (4.8px), .35rem (5.6px) | input and fit-button vertical padding; gap inside `.control`; first message top margin |
| .4rem (6.4px), .45rem (7.2px) | fieldset top padding, message vertical padding; input horizontal padding, button vertical padding |

## Interaction Contract

### Form and schema

1. The form is built from `schema.properties` in property order (= model declaration order: `d`, `pitch`, `left_hand`, `length`, `s`, `k`, `thread_length`). A `fieldset` and `legend` is created per distinct `group`, in first-seen order: `Size` (`d`, `pitch`, `length`), then `Thread` (`left_hand`, `thread_length`), then `Head` (`s`, `k`). `length` and `thread_length` are declared after the field that opened their fieldset and join it. Pinned by `test_the_form_has_a_size_fieldset_then_a_thread_one_then_a_head_one` and `test_the_api_schema_is_the_model`.
2. Control choice: `enum` gives a `select`; `type: boolean` gives `input[type=checkbox]` (no number attributes, natural width: `.field input[type=checkbox] { width: auto; }`); otherwise `input[type=number]` with `inputMode="decimal"`. The branch reads the schema `type` only, never a field name, so a later boolean field needs no JS edit. Pinned by the statements `prop.type === 'boolean'` and `input.type = 'checkbox'`.
3. Bounds: `input.max` is the schema `maximum` (100000 for `d` and `length`, the INTERIM bound `INTERIM_MAX_MM`, D-14). `input.min` is set only from `minimum`, never from `exclusiveMinimum`, because HTML `min` is inclusive and the server's 422 must speak (Pitfall 5). `input.step` is the schema `step` (0.1, 0.05, 0.5), else 1 for integers, else `any`.
4. Help text: `description` is the label's `title` tooltip and a `small` line shown only while the field has focus (`.field:focus-within small`).
5. Typing does not validate in the browser (the form never submits); the server is the only validator (L02, validated once at the model boundary).

### Hash (the shareable link)

6. Grammar: `#[kind=<kind>&]<name>=<value>&...`, serialised with `URLSearchParams`. `kind` first (only when it differs from `/api/kinds` `default`), then fields in form order. Only fields that differ from their default are written. Numbers compare as numbers (`Number(value) !== Number(defaults[name])`), so `6.0` equals the default `6` and is not written; selects and checkboxes compare as strings against `String(defaults[name])`. A checkbox reads as `'true'` or `'false'`, so `left_hand=true` is written only while it is checked and `false` is never written: an omitted key means right-hand on every front end, forever (D-09, L02). An empty field is never written. Pinned by `q.set(name, value)`, `Number(value) !== Number(defaults[name])` and `String(input.checked)`.
7. An empty hash is the default kind with every field at its default. A hash without `kind` means `bolt` forever (D-09, L02).
8. The hash is written with `history.replaceState`: no history entry per edit, no `hashchange` from the page's own writes. When the result is empty the URL is `location.pathname + location.search` with no `#`.
9. Reading: `navigate()` is the single entry for startup, `hashchange` and the kind selector. It reads `kind` (`?? kinds.default`), rebuilds the form only when the kind changed, then sets each control with `write(input, h.get(name) ?? defaults[name])` and builds. `read(input)` and `write(input, v)` are the only way the page touches a control's value, because a checkbox's `.value` is the constant `on`: a checkbox is read as `String(input.checked)` and written as `input.checked = String(v) === 'true'`, any other control by `.value`. So `#left_hand=true` opens checked and an omitted key opens unchecked. A field with no default (the nut's `clearance`) has `undefined` for `defaults[name]`, and `write` turns that into the empty string (`else input.value = v ?? '';`), never the word "undefined" (rule 35). Pinned by `for (const [name, { input }] of fields) write(input, h.get(name) ?? defaults[name]);` and `input.checked = String(v) === 'true'`.
10. A link the page cannot honour is refused whole, like an unknown kind (OI-2, D-10): nothing builds, the form and panel clear, the downloads go, the URL is not rewritten, and one `p.error` names the problem. Checked in this order, by the one helper `refuseLink(message)`: (a) a key given more than once, before the kind lookup (`#d=1&d=2`, `#kind=bolt&kind=bolt`, `#kind=bolt&kind=x`): `The link names "<key>" more than once.`; (b) after the form is built, any key other than `kind` that the kind does not define (`#d=8&m=5`): `Unknown field "<key>" for kind "<kind>". Known fields: <names>.`, `Unknown fields "<k1>", "<k2>" for kind ...` for several; (c) after the values are written, a key whose control cannot hold its value, a checkbox given anything but `true` or `false` (`#left_hand=banana`) or a non-empty value a number or select reads back as `''` (`#d=abc`): `Unreadable value for "<key>": "<value>".`. Parity: the API answers a foreign or repeated key with a 422 and the CLI with exit 2. The next navigation rebuilds the form, as after an unknown kind. `kind` is the only non-field key the page writes. The same helper also clears the picker (`clearPicker()`) and the badge, because the form it would write to is gone. **The preset id and the page's preset basis never enter the hash, the query or any request (Phase 4, D-09):** a link carries the millimetre fields only, so it opens the same part in any build of the page, and the model routes refuse a `preset` key (422 `extra_forbidden`). Pinned by `test_the_ui_refuses_a_link_it_cannot_honour` and `test_the_badge_composes_from_the_status_and_the_display_and_the_basis_stays_in_the_page` (`presetBasis` is absent from `partQuery` and `writeHash`, cleared in `navigate`, and the page's four fetch URLs are the only ones it builds).

### Update loop

11. Typing in any field (`input` event) schedules `update()` after 350 ms, restarting the timer on each keystroke. 350 ms is INTERIM (D-01, carried from spur `app.js:221`, a UI choice never measured for screw; Phase 7 re-sweeps, OPER-02; tracked in `docs/tech_debt/active/2026-10-05-interim-runtime-bounds.md`).
12. `navigate()`, kind change and `Reset` build immediately with no debounce. `navigate()` also cancels the pending debounce and aborts the in-flight request.
13. `update()` sequence: write the hash; clear every `.invalid`; disable both downloads; abort the previous request (`AbortController`); set status `Building…`; fetch `api/<kind>/info?<changed fields>`; on success render the panel, the warnings and the notes and set the picker's selects and the badge from `info.preset` (rule 32); then fetch `api/<kind>/model.stl?<changed fields>&quality=preview`; on success replace the mesh, enable the downloads from that info document's `downloads` with the changed-fields query (rule 17), clear the status.
14. Staleness: a monotonically increasing `seq` discards any response that is not the newest, and a `formSeq` discards a schema response overtaken by a newer navigation (Pitfall 6). `navigate()` bumps both on every call.
15. Failure (any 4xx or 5xx or network error): the messages area shows the error paragraphs, then the warnings and then the notes of the mesh on screen (`mesh ? meshWarnings : []`, `mesh ? meshNotes : []`, OI-3, D-11, D-20); the panel is emptied, the selects go blank and the badge empty (rule 32), downloads stay disabled under their static labels (rule 17), and the status reads `Showing the last valid part` when a mesh exists, otherwise empty. The last valid mesh stays on screen, except across a kind change, which drops it first (rule 36). Warnings belong to a mesh, not to the last info fetch: `renderInfo` keeps the info document's warnings in `pendingWarnings` and `showModel` copies them to `meshWarnings` where it replaces the mesh (`meshWarnings = pendingWarnings`), so a gate `build_error` on the STL request, after its info already rendered, shows the warnings of the older mesh still on screen, not the failing part's. Notes (`info.notes`, D-20) are held the same way (`pendingNotes`, `meshNotes = pendingNotes` in `showModel`), because a note describes the part like a warning does. A refused link (rule 10) and `reportLoadError` show the same. With no mesh (startup failure, first build failed) there are none to show. Pinned by `test_the_ui_keeps_the_warnings_of_the_mesh_on_screen` and `test_the_ui_keeps_the_notes_of_the_mesh_on_screen_like_its_warnings`.
16. The info panel renders before the preview mesh arrives (info is fetched first), so for the length of one STL build the panel can describe a newer part than the mesh shows, and the new info document's warnings are shown with it. `Building…` is on screen during that time.
17. Each download link is built from `info.downloads` by `setDownloads(q, downloads)`, called from `update()` once the preview mesh is on screen: `api/<kind>/model.<format>?<changed fields>&quality=<quality>` for the first entry of its format, in server order, whose `refusal` is null. The first entry of each format is the route's default quality, so the default part shows `Download STL` and `Download STEP`. When that entry is refused the link offers the next served entry and names its quality after the static label of `index.html` (`Download STL (preview)`, the preview tessellation, INTERIM 0.08 mm and 0.5 rad), with the refusal sentence as its `title`; a format with no served entry stays disabled under its static label. The warning stays in the messages (L02: the page names which STL it offers and why). The page reads no warning text and names no format or quality of its own (D-10): the server's order is the preference. The quality and the entries never enter the hash or `partQuery` (D-09). The browser takes the filename from the server's `Content-Disposition` (`<kind>_<fields>.<fmt>`, built by the server from validated floats; it does not name a quality, filed as an idea 2026-10-12). The preview mesh the page shows is always fetched with `quality=preview`. Pinned by `test_the_ui_builds_both_download_links_from_the_info_document_and_names_no_quality` (source) and `test_the_download_labels_are_static_and_the_refused_fine_stl_reads_download_stl_preview` (labels and rule 17 applied to the M8 × 70 and the default document); the document's agreement with the route is pinned by `test_the_downloads_of_iso_4017_m8_x_70_are_one_sentence_on_the_cli_the_api_and_export` (plan 04-15).
18. A disabled download is `a.btn[aria-disabled="true"]` with no `href` (opacity .45, `pointer-events: none`). It is not focusable.
19. `Reset` sets every control to its default through `write(input, defaults[name])` (a checkbox is unchecked; a field with no default, the nut's clearance, is left empty) and runs `update()`. The frozen defaults are the fields of ISO 4017 M6 × 20, so after Reset the selects show `ISO 4017` / `M6` / `20` and the badge reads `matches ISO 4017 M6 × 20` (Phase 4, D-12); the picker has no reset of its own. A link written by Phase 3, which names only fields that differ from those defaults, still opens: no hash key changed. `Copy link` copies `location.href`.

### Kind selector

20. The selector is filled from `/api/kinds` (`new Option(k, k)`). Changing it writes `kind=<k>` (nothing for the default kind) and navigates. A new kind starts from its own defaults and gets its own picker (rule 30); no field carries over on a plain kind change. Carrying `d`, `pitch` and the hand to the other kind is the matching-part link (rule 34, TYPE-04, D-02), an explicit action and not a side effect of the selector (resolved in Phase 5, plan 05-10; the Phase 1 ASSUMPTION is closed).
21. A hash naming an unregistered kind (the same `refuseLink` helper serves rule 10) clears the form, sets `currentKind = null`, deselects the selector, empties the panel, disables the downloads, shows the unknown-kind error and builds nothing. While `currentKind` is null `update()` returns immediately, so no keystroke can build the default part under a link that named another kind (L02).

### Info panel

22. The panel (Phase 4, D-17): when `typeof info.designation === 'string'` an `h2` with that text comes first. Then for each distinct `row.group` in first-seen order (a `Map`, the pattern `buildForm` uses for fieldsets) an `h3` with the group's text and a `dl`; each `info.rows` entry, in server order, is one `div` with a `dt` (`row.label`) and a `dd` (`<String(row.value)> <row.unit>`, trimmed) in its group's `dl`. The page reads `designation`, `rows`, `warnings`, `notes`, `preset`, `downloads` and `counterpart` of `info` (`downloads` only for the download links, rule 17; `counterpart` only for the matching-part link, rule 34), and `label`, `value`, `unit` and `group` of a row. No row is looked up by key and no group name is known to the page. Pinned by `test_the_ui_prints_the_numbers_as_sent_under_the_designation_and_the_groups` and the row-key literal checks (rule 29).
23. Display of the number (met in Phase 4, D-19; OI-1 resolved): the page writes `String(row.value)` and rounds nowhere. There is no rounding helper in `app.js`, and `toFixed`, `toPrecision`, `toLocaleString` and `Intl.NumberFormat` are absent from it. A valid `d` of 0.0004 shows `0.0004 mm`, and the default geometric across-corners row shows `11.547005383792515 mm`: JavaScript prints a double as its shortest round-trip digits, which is what the API sends. Pinned by `test_the_ui_prints_the_numbers_as_sent_under_the_designation_and_the_groups`.
24. Warnings are `p.warning` paragraphs under the downloads, in server order, after any error paragraphs; notes are `p.note` paragraphs after the warnings (D-20). A warning or a note is never truncated or reworded by the page, and the warnings and notes of the mesh on screen are never hidden by an error: they change only when a new mesh replaces it (rule 15, OI-3 resolved). A note is information about the part (a product grade, a wrench size), so it has its own style: muted text on `--bg`, no tint (Color).

### Viewport

25. Z-up camera, perspective FOV 35, hemisphere light plus a directional key light attached to the camera, orbit controls, a ground grid sized to the part (step chosen from 0.5, 1, 2, 5, 10, 20, 50, 100, else 200, so at most 24 cells across, placed 0.01 mm below the part), feature edges at a 40 degree threshold. Pixel ratio is capped at 2. Rendering is on demand, coalesced with `requestAnimationFrame`.
26. The view refits automatically on the first model and whenever the part's bounding-box diagonal changes by more than 30 percent; otherwise the user's camera is kept. `Fit` always refits.
27. Theme follows `prefers-color-scheme`, including live changes; the grid, background, mesh and edge colours are read from the CSS tokens.

### Safety rules (pinned by source assertions)

### Preset picker and badge (Phase 4, D-09, D-10, D-12, D-28)

30. Build: on a kind change `navigate()` fetches `api/presets?kind=<kind>` once, after the form and under the same `formSeq` guard (a response an older navigation started builds nothing), and builds `#picker` with one `label.field` and `select` per entry of `catalogue.axes` (today `Standard`, `Size`, `Length`), each with a blank option first. The Standard select lists the distinct first `picker` strings; the Size select the distinct second strings of the rows whose first string is chosen; the Length select the distinct third strings of the rows matching both; all in catalogue order, second-choice sizes bracketed as the server prints them (`(M7)`, D-28). The page reads `axes`, `rows`, `picker`, `fields`, `id` and `display` of the catalogue and holds no standard, size or length string. A failed fetch refuses the link whole with `Could not load the part: ...` (rule 10's clearing), so the page never shows a form without its picker. The picker is `hidden` until built and again whenever the link is refused. Pinned by `test_the_ui_builds_its_picker_from_the_catalogue_and_writes_fields_only`.
31. Pick: a `change` in any select resolves to one complete row. Later selects holding the blank option or a value no longer offered take their first offered value; then every entry of the row's `fields` is written through `write(fields.get(name).input, value)` (the six millimetre fields; a row defines no handedness, so `Left-hand thread` is left as it was), `presetBasis` is set to the row, and `update()` builds at once with no debounce and no confirmation dialog (the pick is the explicit action and the badge shows the state). A change to the blank option is not a pick: the selects return to what the fields match.
32. The selects track the fields: after each successful info document, when `info.preset.status` is `exact` the three selects show the catalogue row whose `id` is `info.preset.id` (their lists rebuilt for it), otherwise all three show the blank option (the Size and Length lists are then empty until a Standard is chosen). After a failed update the selects are blank and the badge is empty. The `id` is read only to find that row.
33. Badge: composed from `info.preset.status` and `info.preset.display` only. `exact`: `matches <display>`. `custom` while the page holds a basis: `custom, based on <display>`. `custom` with no basis: `custom`. No preset member: empty. The basis is page-session state: the display of the catalogue row the part last matched exactly (a pick lands on one; so does Reset, or an edit that arrives at another row), so a later edit reads "based on" the row the part really was and never a stale pick. `navigate()` clears it, so a reloaded or pasted link whose fields match no row reads `custom`. It is never inferred from the nearest row (L02) and never leaves the page (rule 10). Pinned by `test_the_badge_composes_from_the_status_and_the_display_and_the_basis_stays_in_the_page`.

### Matching part and kind switch (Phase 5, D-01, D-02, D-03, R10, TYPE-04)

34. Matching-part link: `renderInfo` calls `showCounterpart(info.counterpart ?? null)`. A `counterpart` sets the `#counterpart` anchor's `href` to `#` plus `new URLSearchParams({ kind: counterpart.kind, ...counterpart.fields })`, its text to `Matching ` plus `counterpart.kind`, and unhides it; `null`, a failed update (`fail()`) and a refused link (`refuseLink`) hide it. The page names no kind, field, row key or label for it: the server decides what carries over (d, pitch and the hand always; the other standard's `s` and `m`, or `s` and `k`, when the exact (d, pitch) is one of its rows). `clearance`, `length` and `thread_length` are never in `fields`, so a click on a bolt's link opens a nut with the clearance field empty and nothing built (rule 35), and a click on a nut's link opens a bolt with its own default length. A click is a plain hash change: `hashchange` runs `navigate()`, which applies rule 36. Off a row the link is still offered and the source document's last warning says which fields to set (Copywriting Contract). The anchor's `href` is set as a property from server numbers and booleans, never through `innerHTML` (T-05-22). Pinned by `test_the_ui_reads_the_counterpart_by_kind_and_fields_only_and_names_no_kind`; the document by `test_the_cli_and_the_api_print_the_same_counterpart` and `test_following_a_bolts_counterpart_gives_the_nut_row_of_its_size`.
35. A field with no default (the nut's `clearance`, D-01): the form builds it from the schema like any other, with `defaults[name]` undefined. `write(input, undefined)` leaves the control empty, so a link that omits it, Reset and a kind change all open it empty. `partQuery` skips an empty control, so the info request omits the key and the server answers the 422 `missing`: `Clearance (radial): Field required`, the field `.invalid`, the panel empty, the downloads disabled and nothing built. A typed `0` is a legal clearance (a nominal fit, D-04) and is written to the hash: `Number(value) !== Number(NaN)` is always true, so it is never dropped as a default. Do not give the schema a default of `''`: `Number('')` is 0 and a typed `0` would vanish from the link. Pinned by `test_a_field_with_no_default_is_written_empty_never_as_the_word_undefined`.
36. Kind switch (R10, T-05-23): whenever `navigate()` finds the kind changed, whether by the selector or by the matching-part link, `dropMesh()` runs before the form is rebuilt: the mesh and its edges leave the scene, `mesh`, `edges` and `box` are null, the view refits on the next model, and `pendingWarnings`, `meshWarnings`, `pendingNotes` and `meshNotes` are emptied. So a nut with no clearance typed shows an empty canvas and the server's error, never the old bolt under `Showing the last valid part` with the bolt's warnings and notes. Within one kind rule 15 is unchanged. Pinned by `test_a_kind_change_drops_the_old_mesh_and_what_described_it`.

### Accessibility as built

- `#status` is `role="status"`; `#messages` and `#badge` are `aria-live="polite"`; the picker's selects are native elements inside a wrapping `label` whose text is the server's axis name; the canvas has an `aria-label`; every control is a native element inside a wrapping `label`.
- Focus rings are the browser default (`ASSUMPTION:` not verified in a browser). Invalid fields are marked by border colour and outline plus the error text naming the field; no `aria-invalid` is set (OI-5).
